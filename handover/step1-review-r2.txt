SEVERITY: BLOCKING (a hang on some user file; the worker stops reading until restart). The hang itself predates
  these fixes. Finding 9's fix makes it worse: the cap on abandoned reads used to count each reader separately and
  now counts all readers together, so four FIFOs stop every reader, not just one.
WHERE: src-tauri/src/extract/worker.rs:471 (check_before only turns away links and folders) with worker.rs:341-343
  (stuck) and :351 (step returns 0 while stuck). The crawler indexes any non-directory (crawl.rs:24, symlink_metadata),
  and the plain reader takes files with no extension (readers/text.rs:139).
EVIDENCE: rv_real_plain_reader_on_a_fifo_hangs: a FIFO named "pipe" with Registry::platform() is opened, blocks
  in open(), and is abandoned after 10 s: "fifo: abandoned=1 took 10.05s status=("failed", "took longer than 10 s")".
  rv_four_fifos_stop_all_reading: p1..p4.txt are FIFOs and real.txt is an ordinary file. Result: "abandoned=4 queued=1",
  real.txt is never read, and the test fails with "a real file is never read while four fifos hang". In the app,
  run() then waits idle_poll and gets 0 again, forever. The four threads stay blocked until the app quits. Writing
  to a FIFO changes its mtime, so a FIFO in use is queued again after every write.
SUGGESTED CHANGE: in check_before, after the link check: if !meta.file_type().is_file() && !(meta.is_dir() &&
  reader.packages()) { return Ok(Ok(Finished::Clear(job))) }. This turns away FIFOs, sockets and devices before
  open(). Add rv_four_fifos_stop_all_reading as a regression test.

FINDING 2: A folder removed while its scan is still running comes back, and nothing ever removes it
SEVERITY: BLOCKING (the names and the text read from a removed folder stay searchable after the removal). The race
  is the same one phase 1 had for names, but now the worker also reads these leftover rows. Finding 4 is about
  folder removal, and its fix doesn't cover a scan that is still running.
WHERE: src-tauri/src/app.rs:115-122 (remove_folder) and start_scan app.rs:166-198 (no way to cancel; crawl::scan
  walks to the end, upserting with root=<removed>); db.rs remove_root_in_batches stops at the first empty batch
  and clears the mark
EVIDENCE: rv_scan_after_removal_leaves_rows_nobody_removes. Sequence: add_folder, forget_folder, then
  remove_root_in_batches runs to the end, then the scan that was in flight finishes. Output: "left behind after
  removal: 31 rows, folders=[], removals=[]". No folder row and no removal mark remain, so the next start neither
  scans nor removes these rows. The worker reads them, and they turn up in name and text search. Realistic case:
  the user adds a big folder by mistake and removes it while it is scanning.
SUGGESTED CHANGE: keep a cancel flag per scanning root (scanning: HashMap<String, Arc<AtomicBool>>). remove_folder

  leftovers from any race (and from phase 1 indexes) are cleaned up.

FINDING 4: The new "1 zero in 16" rule rejects BOM-less UTF-16 text with few spaces (Japanese, Chinese) as binary
SEVERITY: MINOR
WHERE: src-tauri/src/extract/decode.rs:85 (enough: zeros * 16 >= head.len() / 2)
EVIDENCE: rv_decode_cases, run on the copies before and after the fix:
  "ja utf16le nobom": before enc=UTF-16LE "東京都の天気は晴れ…", after ERR Binary. Japanese has no spaces, so its
  only zero bytes come from newlines and ASCII, about 1 in 37 code units, which is under 1 in 16.
  "zh"/"ko" samples are Binary both before and after. That was already true: U+4E00 一 and U+AC00 가 have a zero
  low byte, so the zeros fall on both sides and fail even*20<=odd.
  The tiny edge cases are still there: "abc\0def\0" still decodes as UTF-16LE "扡c敤f", and a 2-byte UTF-16 "a" is
  now Binary. Neither matters.
SUGGESTED CHANGE: the case to reject is one or two stray zeros, so a much lower share is enough, e.g.
  zeros >= 2 && zeros * 128 >= head.len() / 2. Keep the ja sample as a test.
  Alternatively (more robust) look at the other side's bytes: in real UTF-16 the high bytes are few distinct values
  (a script block), while 8-bit text read as UTF-16 has dozens.

FINDING 5: Unclaiming on error means a write error that keeps happening re-reads the same batch every 5 s, without end
SEVERITY: MINOR (it needs a database error that persists after a successful claim; reads are spaced idle_poll apart)
WHERE: src-tauri/src/extract/worker.rs:345-366 (step's error path) and run() :244-247 (Err => wait idle_poll and go on)
EVIDENCE (reading, and the builder's an_error_after_a_claim... test, which reads all three files again on each of
  its 3 failing runs). A disk that is almost full is enough: the claim's small write fits, but a 4 MB text write
  fails. The files go back with attempts undone, the next step claims and reads the same batch, and this repeats
  every 5 s for as long as the error lasts. Before the fix the attempts piled up until the files were recorded
  failed (with the wrong reason), so the loop ended. There is also a second, smaller problem: when settle fails
  part way through a batch (the batch_bytes write at :452), the reads still running are dropped without being
  counted in `abandoned`, so the global cap of 4 undercounts stuck threads.
SUGGESTED CHANGE: back off after consecutive Err from step (double the wait, up to e.g. 10 min, and reset on Ok).
  On the error path, count the reads still running as abandoned (fetch_add for every flight in RUNNING state, as
  the timeout path does), or wait for them up to their deadline.
