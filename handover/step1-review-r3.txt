FINDING 1: A folder removed during its scan and added again before that scan has left `scanning` is kept but never scanned
SEVERITY: BLOCKING (a kept folder's files are never indexed, until the next start or a change of ignore rules)
WHERE: src-tauri/src/index/folders.rs:134-139 (scan() returns when the root is already in `scanning`, even when
  that scan is cancelled) and :157-168 (the cancelled scan then only calls start_removal, whose thread sees the
  folder in `folders` again and does nothing, :191-193)
EVIDENCE: rv3_readd_while_cancelled_scan_ends_is_never_scanned. Steps: add Docs (2100 files), the scan writes
  its first batch and is held there (the Progress hook, as the builder's own test does); remove Docs; add Docs
  -> refused "still being removed" (this starts a removal); that removal deletes the 2000 rows and clears the
  mark; add Docs again -> accepted, app.rs then calls folders.scan(Docs), which is a no-op; the held scan sees
  its cancel flag and stops. After everything is idle:
    rv3 readd: folders=["/tmp/.tmpjtedJv/home/Docs"] rows=0 removals=[]
    panicked: kept folder not fully indexed: 0 rows of 2111
  In the app, the window is the time a scan spends between two cancel checks: an upsert waiting on writer()
  (the worker or a removal batch holds it), or walkdir's next() blocked on a slow or network disk. The user is
  told "add it again in a moment", so a quick second click is the expected use. The watcher is added again, so
  later changes are indexed, but the files already there are not, and the remove_unseen pass never runs.
SUGGESTED CHANGE: when scan() finds the root scanning with its cancel flag set, record that a fresh scan is
  wanted (e.g. scanning: HashMap<String, (Arc<AtomicBool>, bool /*rescan*/)>, or reset the flag to false), and
  have the scan thread, on ending cancelled, start a new scan if the folder is in `folders` again, and a removal
  otherwise. Also make the removal's "added again?" check atomic with its deletes: in remove_root_in_batches use
  "DELETE ... WHERE root = ?1 AND NOT EXISTS (SELECT 1 FROM folders WHERE path = ?1) LIMIT ...", because the
  "again" pass of a removal runs with no mark, so add() can succeed between its folders() check (folders.rs:191)
  and its deletes (I could not hit that window in 30 rounds of rv3_readd_during_the_again_pass_of_a_removal:
  the first delete of that pass is empty and fast, so it is only a note). Keep rv3_readd_... as a test.

FINDING 2: Removing a child folder that sits inside another folder removes the parent's files under it
SEVERITY: BLOCKING by the rule (a kept folder's rows are lost after things settle), but it predates round 2:
  phase 1 (2e43773) has the same add check and removes by root. Round 2 does not cause it and does not make it worse.
WHERE: folders.rs:102-106 (add refuses a child of a folder, not a parent of one, so P can be added after P/C);
  db.rs remove_root_in_batches (deletes by files.root); upsert rewrites root, so the rows under C have root C or P
  depending on which folder was scanned last (scans run in any order at start and after set_ignore)
EVIDENCE: rv3_removing_a_nested_child_folder_keeps_the_parents_files: add P/C, scan; add P, scan; scan P/C again
  (as a restart or set_ignore does); remove P/C. Result:
    rv3 nested: folders=["/tmp/.tmpZfKOdD/home/P"] rows under C=0
    assertion `left == right` failed: P is still a folder, its C files must stay  left: 0  right: 20
  The same happens the other way (remove P, keep C: C's rows with root P go), and to the NOT_REMOVING search
  filter while it runs. mark_orphan_roots does not add to it: both roots are in `folders`.
SUGGESTED CHANGE: when a parent is added, drop the child folders it contains (forget them without removing
  rows), or refuse the parent, so roots never nest. Or, after a removal, rescan every folder that contains the
  removed root.

CHECKED WITHOUT FINDING
- Deadlocks: the jobs lock is never held while writer() is taken or on_event runs. remove() takes writer (in
  forget_folder) and then jobs, separately. The scan and removal threads take jobs only for map updates, and the
  worker's pause closure (is_scanning) takes it only briefly. app.rs holds the reader Mutex across folders.add or
  remove, and no background thread takes that Mutex. Index::open takes writer() but holds no other lock.
- Removal waits for the scan: cancel is set under the jobs lock that the scan thread reads it under when it ends,
  so the scan either sees the flag or has not ended yet. Mutation M3 (the scan ignores cancel) is caught.
- Re-add during an ordinary removal: add() is refused while the mark exists and starts the removal again (M8 is
  caught). The "again" pass rechecks folders() first. I could not make the non-atomic window lose rows in 30
  rounds of rv3_readd_during_the_again_pass_of_a_removal (see the note in Finding 1).
- Parent or child added during a removal or a cancelled scan: upsert rewrites root, so a re-added parent or child
  takes its rows over. The remaining nested-folder problem is Finding 2, which predates round 2.
- Crash or restart: forget_folder sets the mark in the same transaction that removes the folder row. resume()
  marks orphan roots, scans folders, then resumes removals.
- mark_orphan_roots: with P, P/C and Q all folders and rows under each root, it marks 0. It compares files.root
  with folders.path as exact strings. add() canonicalises paths, and the scan and the watcher write the folder's
  own string as root, so spellings agree. A folder row with a trailing slash would be marked orphan and its rows
  removed (rv3_mark_orphan_roots_spellings: marked 1). That cannot happen through add_folder, in phase 1 or now.
- One defensive note: a removal whose root is in `folders` returns Ok(None) and leaves the mark in place. If a
  folder row and a mark ever existed together, NOT_REMOVING would hide that folder from searches for good. I found
  no sequence that produces this state.
- Non-regular files: record_of skips FIFOs, sockets and devices, and keeps files, folders and links as before. A
  refresh of a path that became a FIFO calls remove_tree. check_before clears anything that is not a regular file
  or (for a packages reader) a folder, and links are cleared as before. M1 and M2 are both caught.
- Tokenizer: the concat! string builds; rv3 opening an f460f88 database passes both FTS integrity checks
  (Finding 4).
- Decode: 1 in 128 accepts the Japanese sample, and two stray zeros in 900+ bytes are still Binary. M10 is caught.
- Backoff: doubling up to 600 s (M11 caught). Stop stays prompt during a long backoff: 0.4 ms. Wakes do not end
  the backoff (rv3 test).
- Abandoned counting on the error path: CAS from RUNNING to ABANDONED, then fetch_add. A read that finishes
  later does fetch_sub, so the count is balanced. M12 is caught.
- NOT_REMOVING: an uncorrelated subquery over a key range of meta, read once per statement, so it is cheap.
  substr(key,10) matches the 9-character "removing:" prefix. It filters by exact root, so with nested roots it
  hides exactly the rows the removal will delete (see Finding 2). Both name searches (exact and typo-tolerant)
  and match_contents use it. M6 is caught.
- Mutations 12 of 14 caught (M4 is harmless, M13 is caught by my rv3 test, M14 is not caught).
- Flakiness: lib suite with the rv3 tests skipped, 3 runs: 90/90 each time (7.4 s, 9.2 s, 10.3 s, with another
  heavy job running).
