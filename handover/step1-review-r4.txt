FINDING 1: Removing a folder that was taken in stops the watcher for that part of the outer folder (Linux)
SEVERITY: BLOCKING by the rule ((b) is broken through the remove_folder command), but the current window
  does not offer it: it reloads the folder list after adding, so the user only gets there with a stale list
  or by calling the command directly. The same thing already happened in phase 1 with real nested folders.
WHERE: src-tauri/src/app.rs:111-117 (remove_folder calls watch.remove_root(path) before folders.remove finds
  that path is not a folder); src-tauri/src/index/watch.rs:78-82 (unwatch result ignored). notify 6.1.1
  inotify.rs:437-468: its watch map holds every subfolder that P's recursive watch added, so unwatch(P/C)
  finds P/C, and rm_watch drops P/C and every watch under it.
EVIDENCE: rv4_removing_a_taken_in_folder_keeps_the_outer_folder_watched. It does what app.rs does: add P/C,
  watch it, add P (unwatch the folders taken in, then watch P), scan P. A file created in P/C is indexed (so
  P's watch covers C). Then remove_folder(P/C): watch.remove_root(C), then folders.remove(C), which does
  nothing, as the plan says. Then it creates P/C/after.txt and P/control.txt:
    control indexed; panicked: "P is still a folder, but P/C/after.txt was never indexed"
  Nothing under P/C is kept current until the next start or a change of ignore rules. The plan says
  "removing a folder taken in does nothing", and the builder's test only checks that at the Folders level.
  On macOS (FSEvents), unwatching a path that is not a watch root returns an error, which is ignored, so I
  expect no effect there (not checked here).
SUGGESTED CHANGE: in remove_folder, unwatch only a path that is a folder: call folders.remove first and have
  it return whether it forgot a folder (forget_folder already returns that), then call watch.remove_root
  only if true. Or check state.reader.folders() first. Keep the rv4 test (Linux only).

FINDING 4: A watcher batch that began before a take-in (or a removal) writes rows under the old root
SEVERITY: MINOR (the race the folders.rs module doc already accepts: "rows still left (from a race with the
  watcher ...) are found at the next start". This round adds the take-in case)
WHERE: src-tauri/src/index/watch.rs:56-64 (the roots are copied once per batch); crawl.rs:141-145
EVIDENCE: rv4_a_watcher_refresh_with_old_roots_after_a_take_in (it calls refresh with the roots the watcher
  read before add_folder changed them): C is a folder and scanned; add P (takes C in); scan P; a refresh of
  P/C/rv4zebra.txt with roots [C]; remove P:
    rv4 watcher: roots=[(".../home/P/C", 1)] hits=1
    panicked: after removing P: rows whose root is not a folder: [(".../P/C", 1)] (folders [], removals [])
  Until P is removed, the row only has the wrong root (P's next scan fixes it), but P's removal does not
  delete it, and it stays searchable until the next start. With a large burst (a git checkout under P/C),
  the window is the length of the batch.
SUGGESTED CHANGE: have refresh pick the root from the `folders` table (in the upsert's transaction), not
  from the watcher's copy, or skip a path whose root is no longer a folder. Either one also covers the old
  remove case.
