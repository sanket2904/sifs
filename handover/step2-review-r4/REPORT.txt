FINDING 1: Duplicate attributes take quadratic time inside one event, and the deadline is never checked
SEVERITY: BLOCKING
WHERE: src-tauri/src/extract/readers/office/mod.rs:541 (attr), :551 (rel_id); quick-xml 0.42 events/attributes.rs:1061-1092
EVIDENCE: attr() uses e.attributes().flatten(). quick-xml checks for duplicate names by default. For a tag
  with many attributes, a new name costs O(1) (hash prefilter), but each duplicate falls back to a linear
  scan of every earlier key. flatten() throws the Duplicated error away, and the search continues to the
  next attribute. The whole scan happens inside one handler call, so walk() never reaches sink.check().
  A tag stays under the 4 MB event cap. Word calls attr() on every w:br; Excel calls it twice on every c.
  r4_duplicate_attributes_obey_deadline (Word, one <w:br> with 50,000 distinct attributes, then 50,000
  repeats of the last one; 114 KB file), debug build:
    duplicate attributes: zip=114010 event=1100007 elapsed=35.979340375s  -> FAILED (limit 10 s + 5 s grace)
  r4_duplicate_attributes_release (--release --ignored):
    unique=50000  dups=50000  tags=1 zip=114010  elapsed=3.86s
    unique=150000 dups=150000 tags=1 zip=342850  elapsed=37.9s
    unique=150000 dups=150000 tags=4 zip=1368230 elapsed=150.0s
  The time grows with the number of such tags, up to the 128 MB unpack cap (about 38 tags, roughly 24 minutes).
SUGGESTED CHANGE: Use e.attributes().with_checks(false) in attr() and rel_id(), and take the first match.
  Office files never repeat attributes, and nothing here needs the check. I tried this change: the test
  then passes and all other office tests still pass. I reverted it afterwards. Another option is to stop
  scanning after a fixed number of attributes, say 1,000.

FINDING 2: Resolved relationship targets have no total memory bound (50,000 copies of a long folder)
SEVERITY: BLOCKING
WHERE: src-tauri/src/extract/readers/office/mod.rs:580 (Rel { target: resolve(&self.dir, &target) }), :560 MAX_RELS;
  powerpoint.rs:56 (each slide's .rels)
EVIDENCE: Each raw Target is under the 4 KB attribute limit, but resolve() prefixes the folder of the part
  the relationship belongs to. That folder is already the product of earlier resolutions. In PowerPoint the
  chain runs root .rels (4 KB) -> presentation -> slide (8 KB folder). Then each of the slide's 50,000
  relationships, with Target="x", is kept as about 8 KB. All of them are held in one Vec<Rel> while
  .find(notesSlide) runs.
  r4_resolved_relationships_have_a_total_memory_bound (no caps raised):
    path expansion: zip=174442 peak=386 MiB elapsed=544ms        (full PowerPoint read, held::peak)
    path expansion: relationships=50000 retained=405407482 bytes (386 MiB) inflated=2538921   -> FAILED
  Word and Excel have the same problem one level up: the main part's .rels. r4_word_document_relationships_have_a_total_memory_bound:
    word path expansion: zip=142588 peak=196 MiB  -> FAILED (assert < 128 MiB; 50,000 x 4 KB from a 143 KB file)
  Round 2's 50,000 limit (r2_relationship_path_memory) bounds the count of relationships, not the bytes they hold.
SUGGESTED CHANGE: Bound the bytes, not just the count. Either keep a running total of resolved target bytes
  per .rels part (for example 4 MB, the event cap) and stop there with note_truncated, or drop any resolved
  target longer than MAX_ATTR or not in Package::names. The second option on its own still allows
  50,000 x 4 KB = 200 MB, so pair it with the total. For slides, only the notesSlide relationship is
  needed: a Rels handler that keeps only the wanted kinds would avoid the Vec entirely.

FINDING 3: The nesting cap limits the number of open elements, not their names' bytes
SEVERITY: BLOCKING (the same mechanism and measurement that round 3 counted as blocking)
WHERE: src-tauri/src/extract/readers/office/mod.rs:463 MAX_DEPTH, :496-505 (walk); quick-xml reader/state.rs:337-353 (opened_buffer)
EVIDENCE: quick-xml copies every open element's name into opened_buffer (a String that grows by doubling).
  Depth stops at 10,000, but each name is limited only by the 4 MB event cap. So the open names can fill
  everything that can be unpacked (128 MB), and the buffer's doubling reserves up to twice that.
  r4_open_element_names_have_a_total_memory_bound: 9,991 nested elements with 12 KB names (a random tail
  keeps the part under the 100:1 bomb ratio). The first name is sized so the last doubling falls just
  under the unpack cap:
    open names: xml=242275678 zip=1968084 peak=330 MiB elapsed=889ms result=Ok(... "truncated","1")  -> FAILED
  That is 220 MiB reserved, plus the old 110 MiB block while realloc copies it, from a 1.97 MB .docx.
  The same counter measured round 3's 290-418 MB.
SUGGESTED CHANGE: In walk(), treat a Start whose name is longer than a small limit (256 bytes is plenty;
  Office names are under 64) as Walked::Long. Another option is to keep a running total of open name
  bytes (add on Start, subtract on End using a Vec<u16> of lengths) and stop past about 1 MB. Either
  keeps opened_buffer to a few MB.
