Round 4's three fixes are right, and each has a test that fails without it (see CHECKED). The remaining class
of problem is handler work that grows with what earlier parts left behind rather than with the current event.
walk() asks the sink only every 4,096 events, so that interval is bounded only if every event is cheap.
Two handlers break this; the first is blocking.

FINDING 1: A cell naming a blank shared string re-scans the whole string, and the sink isn't asked for 15 s at a time
SEVERITY: BLOCKING
WHERE: src-tauri/src/extract/readers/office/excel.rs:474 (`shown.trim()` in Sheet::close for `c`), :198 (shared strings stored untrimmed);
  office/mod.rs:490 (the sink is asked once every CHECK_EVERY = 4,096 events)
EVIDENCE: One shared string of 3,999,999 blank characters (allowed by shared_chars; split into 3 MB runs so each text event is under
  the 4 MB event cap). Each `<c t="s">0</c>` names it. On every close, `shown.trim()` walks all 4 million characters, finds nothing
  left, and returns without calling the sink, so Sink::text never calls check(). If one `<v>` wraps a row's cells, each cell is
  3 events, so one check interval covers 1,365 cells. Cheap empty comments in front set where the checks fall, so one lands just
  before the deadline.
  r5_blank_interval_release (#[ignore], --release): time for one check interval
    cells=819  (5 events each), U+3000 only:            3.8 s
    cells=1365 (3 events each), U+3000 only:            6.4 s
    cells=1365, blanks of mixed widths (1-3 bytes):    14.7 s   (zip 3.2 MB)
  r5_blank_shared_string_cells_ask_the_sink_in_time (10 s deadline, as the worker sets it; 3.5 MB file):
    release: elapsed=23.96s result=Err("Timeout")   -> FAILED (assert < 15 s)
    debug:   elapsed=117.3s result=Err("Timeout")   -> FAILED
  With no deadline, the 1,000,000-cell cap would mean about 3 hours of CPU. The sink stops it at the first check after the
  deadline, up to 15 s late in release (2.4x the limit) and about 2 minutes late in debug. Round 2 rated the 24 s styles case BLOCKING.
SUGGESTED CHANGE: Store each shared string trimmed when Shared::close pushes it. Every cell shows it trimmed anyway, so the output
  is unchanged, and a blank string becomes empty. A cell then costs O(1) here, plus at most a contains/replace pass over text
  that goes to the sink. Tried in the copy (`let t = s.trim(); push(if t.len()==s.len() {s} else {t.to_string()})`): the test then
  passes and the other 197 tests pass. Reverted. As general protection, also count a handler's work, not just events,
  toward the next check: for example, ask the sink whenever the bytes a handler scans since the last check pass a few MB.

FINDING 2: Past 25,000 parts, every page break re-trims the last kept part
SEVERITY: MINOR (5 s per check interval in release; 60 s in debug)
WHERE: src-tauri/src/extract/mod.rs:190 (Sink::part: `last.text.trim().is_empty()` runs before the parts_full test)
EVIDENCE: After 24,999 pages of "x", the 25,000th page holds about 930,000 blank characters, then "x". A run over 64 KB is written
  as it comes, so the blank characters reach the sink. Then 2,048 `<w:br w:type="page"/>` follow (4,096 events, one check interval).
  Each break calls Sink::part. It trims the whole last part again, finds text, sees parts.len() >= MAX_PARTS, and returns.
  Nothing changes, so the next break pays the same cost.
  r5_parts_full_retrims_the_last_part_per_break (857 KB file):
    release: 0 breaks 26 ms, 2048 breaks 5.04 s   -> FAILED (assert difference < 1 s)
    debug:   0 breaks 310 ms, 2048 breaks 60.3 s  -> FAILED
  A part's text is capped at 1M characters, so this is the same class as finding 1 at a quarter of the size.
SUGGESTED CHANGE: Return at the top of Sink::part when parts_full is set. The last kept part has text then, and nothing more is
  taken. Alternatively, keep a "last part has text" flag, set in Sink::text, instead of trimming. Tried the first version in
  the copy: the test passes (2048 breaks: +36 ms in debug), and all other tests pass. Reverted.

FINDING 3: A zip64 end record makes the zip crate reserve room for every entry it declares, before reading one
SEVERITY: MINOR (it needs a file near the 100 MB size limit; for files of a few MB it stays small)
WHERE: src-tauri/src/extract/readers/office/mod.rs:218 (ZipArchive::new); zip-9.3.0 src/read/zip_archive.rs:329-330
  (`IndexMap::with_capacity(file_capacity)`, `Vec::with_capacity`)
EVIDENCE: The zip crate takes the declared entry count, up to file length / 47 for zip64, and reserves that many entries before it
  reads a single header. The 4 MB directory budget only counts bytes read, so it doesn't apply. The test file is zeros followed
  by a zip64 end record, locator and end record (it compresses to almost nothing).
  r5_zip64_declared_entries_reserve_memory_before_reading:
    file=4 MB  peak=14 MiB  result=Err("damaged or incomplete: ... Invalid Central Directory header")
    file=99 MB peak=373 MiB result=Err(same)   -> FAILED (assert < 256 MiB)
  Most of the reservation is never touched, so resident memory stays small, and macOS won't refuse a 373 MB virtual allocation.
  By the allocator count these reviews use, though, it is over the line, from a file the reader accepts (MAX_BYTES 100 MB).
SUGGESTED CHANGE: Before ZipArchive::new, read the end record (the last 22 + 65,535 bytes) and any zip64 record yourself. Refuse
  the file ("more than {entries} parts") if the declared count is over caps.entries. Office files never use zip64 entry counts.
