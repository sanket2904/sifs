FINDING 1: Empty deflate blocks: a 4 MB workbook runs for 29 s and never asks the sink
SEVERITY: BLOCKING
WHERE: src-tauri/src/extract/readers/office/mod.rs:417-433 (Inflate counts only output) and :280 (parts are read through
  zip's by_index, so flate2 loops inside a single read()); excel.rs:36-64 (six parts are read before the first per-sheet
  check). The same happens in word.rs (5 parts) and powerpoint.rs (4 parts, then 3 per check).
EVIDENCE: An empty fixed-Huffman deflate block is 10 bits and unpacks to nothing. miniz_oxide rebuilds its tables for each
  block (about 1.6 us per block). flate2's read() loops until it has output. So one read() over N MB of such blocks takes
  about 1.2 s per MB in release, with no event and no check. The bomb ratio, the 128 MB unpacking cap and the event cap
  all count output, so none of them applies. The zip crate checks overlapping entries only when asked, so several central
  records can point at one local header: one stored copy of the data is unpacked once for each part name.
  r6_empty_blocks_release (#[ignore], --release; one part, _rels/.rels, 10 s deadline):
    file  1 MB:   1.3 s   ok
    file  4 MB:   4.8 s   ok
    file 10 MB:  12.7 s   Timeout
    file 40 MB:  46.1 s   Timeout
    file 99 MB: 118.8 s   Timeout  (MAX_BYTES is 100 MB)
  r6_six_stalls_release (#[ignore], --release, 10 s deadline). _rels/.rels, docProps/core.xml, xl/workbook.xml, its .rels,
  sharedStrings.xml and styles.xml are one stored XML behind empty blocks:
    file 1 MB: 10.0 s   result Ok
    file 2 MB: 15.9 s   result Ok
    file 4 MB: 28.6 s   result Ok   (the sink was never asked; the deadline passed unnoticed)
  At 99 MB this would be about 12 minutes of CPU. The worker abandons the read after its grace period, but the thread keeps
  running. With 4 abandoned reads (MAX_ABANDONED), no more files are read until one of them ends.
  r6_empty_blocks_ask_the_sink (normal test; the time is already up; a 256 KB file, the same six parts):
    debug: elapsed=18.5 s result=Ok(0)  -> FAILED (assert < 1 s)
SUGGESTED CHANGE: Make the compressed side ask the time. For example, give Budgeted (the file under the zip crate, which
  every part's compressed bytes pass through, in reads of at most 32 KB) the sink's deadline. Its read() returns an error
  once the deadline has passed. Package::parse then maps a by_index or XML error to Timeout when sink.check() fails.
  I tried this in the copy (Rc<Cell<Option<Instant>>> set from sink.deadline in parse; reverted). The test above then
  stops in 0.4 ms with Timeout, and the other tests pass except review2::r2_events_span_small_parts. That test pins
  that 256 tiny parts go by before the first check, and would need to say "at the latest". A ratio cap alone (compressed
  bytes read against output) is not enough: blocks holding one literal each give out 1 byte per 2.25 compressed bytes
  and are nearly as slow.

FINDING 2: The declared-entries pre-check reads only one end record; the zip crate falls back to others
SEVERITY: MINOR (as in round 5, it needs a file near 100 MB, and the reservation is virtual)
WHERE: src-tauri/src/extract/readers/office/mod.rs:365-390 (declared_entries)
EVIDENCE: zip 9.3 tries every end-record signature in its window, from last to first, and falls back past one that fails.
  Its window is the last 22 + 4 + 65,536 bytes, against declared_entries' 22 + 65,535. When the locator does not point
  exactly at a zip64 record, the zip crate scans forward from where it points, and declared_entries ignores it.
  r6_declared_entries_can_be_got_round (99 MB files, round 5's zip64 claim of len/47 entries):
    plain (round 5's file):                     peak=0 MiB   "more than 10000 parts"  (the fix works)
    locator pointing 1 byte early, count 0:     peak=373 MiB  -> FAILED
    stray end record after the real one:        peak=373 MiB  -> FAILED
    end record 65,560 bytes from the end:       peak=373 MiB  -> FAILED
SUGGESTED CHANGE: Look at what the zip crate looks at. Take the largest count over every end-record signature in the last
  22 + 4 + 65,536 bytes. For each record with a locator, look at every zip64 signature between the locator's offset and
  the locator (the zip crate would read that range through the 4 MB budget anyway, so it is at most 4 MB). Or refuse a
  file whose locator does not point exactly at a zip64 record.
