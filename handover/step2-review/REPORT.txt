FINDING 1: One shared string repeated across a row multiplies memory without bound (OOM abort of the app)
SEVERITY: BLOCKING
WHERE: src-tauri/src/extract/readers/office/excel.rs:358 (Sheet::shown clones the shared string) and :410/:414-417 (cells pile up in self.row until </row>)
EVIDENCE: review_excel_row_of_one_shared_string_repeated_grows_memory_past_caps: a 649 KB .xlsx whose
  sharedStrings holds one 1,000,000-character string (a quarter of the 4M shared_chars cap) and whose one
  row has 300 cells <c t="s"><v>0</v></c>. Run alone:
    peak memory grew by 571 MB; ok=false
    panicked at review.rs:148: peak memory grew by 571 MB for a 648956 byte file
  The row is only handed to the sink (which caps at 1M chars) at </row>, so every cell's clone is held first.
  Each cell costs ~25 bytes of XML; the cell cap is 1,000,000 and the shared cap 4M chars, so one row of
  a few thousand cells asks for tens of GB. sink.check() is only every 4,096 events (~800 cells = 3.2 GB
  at the 4M cap) and does not bound memory at all. A Rust allocation failure aborts the whole process:
  catch_unwind in worker.rs:573 does not catch it, so the app dies, and on restart the file is read again
  (the "stopped twice" rule ends it after 3 tries, i.e. the app crashes up to 3 times per such file).
SUGGESTED CHANGE: bound the row: keep a running byte count of self.row and, once it passes the sink's
  remaining room (or LONG_LINE, as Prose does), write what is there and stop pushing; or write each cell to
  the sink as it closes (joined with \t, \n at </row>). Also don't clone: borrow the shared string when
  composing. Add a test with one big shared string referenced many times in one row.

FINDING 2: Slide and sheet lists are matched to relationships by a linear search with no time check: hours of CPU per file, and 4 such files stall the worker
SEVERITY: BLOCKING
WHERE: src-tauri/src/extract/readers/office/powerpoint.rs:566-567 (rels.iter().find per sldId); excel.rs:71-72 (same per sheet)
EVIDENCE: review_pptx_slide_list_against_missing_ids_is_quadratic_and_unchecked: presentation.xml with 60,000
  sldId r:id="x{i}" and a .rels with 60,000 relationships whose ids never match (311 KB file):
    pptx linear (1 rel): 159938 bytes, 245.822824ms, result Ok(0)
    pptx quadratic: 310943 bytes, 42.997177952s, result Ok(0)
    panicked: time limit 10 s, took 42.784864217s; result Ok(())
  The loop over slides never calls sink.check() (a missing rel just continues, and walk() resets its event
  counter per part), so the read runs past the 10 s limit and even returns Ok. Within the 128 MB unpack cap
  about 1.6M of each fit, ~700x the work above: hours. The worker abandons the thread at the time limit but
  it keeps a core busy; at MAX_ABANDONED = 4 (worker.rs:29) no more reads start at all until they end, so four
  such files stop all reading inside files for hours. The plan says "a reader past its time stops itself,
  rather than being abandoned" - not true here. Excel has the same shape (sheets x workbook rels).
SUGGESTED CHANGE: build a HashMap<id, target> from the rels once (O(n)), and call sink.check() in the
  per-slide/per-sheet loops. Consider capping the number of slides/sheets (e.g. caps.entries).

  Related, same root cause (no sink.check() between parts): review_many_sheet_entries_to_one_empty_sheet_never_ask_the_sink:
  a workbook with 400,000 <sheet r:id="rId9"/> entries all pointing at one empty sheet (each parse < 4,096
  events, no text, so walk() never asks the sink):
    400000 sheet parses: 29.774322365s, result Ok(())   (limit 10 s)
  Linear and bounded by the 128 MB unpack cap (~1.3M parses, ~100 s debug), so less severe, but it is
  also past the limit and returns Ok. The same works for PowerPoint (many sldIds to one slide).
  SUGGESTED CHANGE (both): sink.check()? at the top of each per-sheet / per-slide iteration; and/or keep
  walk()'s event counter on the Package so it spans parts.

FINDING 3: A Word table cell is held whole (then split and re-joined): ~4x the unpack cap in memory
SEVERITY: MINOR
WHERE: src-tauri/src/extract/readers/office/mod.rs:653-663 (LONG_LINE flush only looks at self.line) and :675-676, :636-637 (cell grows, then split_whitespace().collect::<Vec<_>>().join)
EVIDENCE: review_word_table_cell_is_not_written_as_it_comes (run alone): 40 MB of words in one cell:
    table cell: peak grew by 161 MB for 40 MB of text; ok=true
  review_word_paragraph_memory_baseline, the same 40 MB as a paragraph:
    paragraph: peak grew by 1 MB for 40 MB of text
  Bounded by the 128 MB unpack cap (so ~0.5 GB at worst, no crash), but the paragraph path's design
  ("a paragraph can be as long as the part: write it as it comes") is not applied to cells or rows.
  Same class, by reading: sharedStrings has no cap on the number of <si> (only on characters), and each
  one past the cap still pushes a String (24 bytes) for a 5-byte "<si/>"; a stored (ratio 1) sharedStrings
  of ~100 MB is ~0.5 GB of Vec<String>.
SUGGESTED CHANGE: stop appending to self.cell (and to self.row) once it passes the sink's remaining room
  or LONG_LINE; the rest of the cell can't be kept anyway. Cap the number of shared strings (e.g. at
  caps.cells) and stop the part once past it.

FINDING 4: Page breaks inside a table are dropped, so every page label after a multi-page table is short

EVIDENCE: by reading; mutation "page break in table not ignored" is NOT CAUGHT by the suite (no test of a
